summary

Between 21 and 28 October 2026 I wrote a compiler that turns Emmy's Kernel IR into PTX. It is one Python process, one emission walk over the statement tree after a few analysis scans, and no CUDA C++ intermediate. The public artifact is 200 files at commit 4018a9e, tag v1.0.0. It passes 15/15 open problems on the hosted runner twice, 46/46 checked-in variants, 86/86 generated corpus IRs in 85 packages, 147/147 local IR compilations, 8/8 holdout shapes in the audit, and 92 unit and contract tests. The 88-cell matrix reports absolute medians and a disclosed residual. The 43x in the title is the ratio of the first working compiler's local time to the fast end of the m01 reference range, not the speedup of the later fix.

The two 15/15 runs were on the code-identical working revision 9b81f01 before the release commit; the exact tagged tree was not itself launched on the hosted runner.

The story is not a feature list. A compiler is a stack of promises about which thread is active, which register is live, and which memory is initialized. The work is finding the promise that is false. Three promises survived contact with the GPU: the launch is the contract, accumulator ownership belongs to the loop statement, and state read under a predicate must be defined unconditionally. The speed work became measured changes, several of which the machine rejected.

This post explains the pipeline, the three invariants, the 43x index bug, the shared-memory and warp-level mechanisms, the negative results, the verification ladder, and the seven edge cases outside the proof. It also states where the evidence stops: the public CSV carries absolute medians, not the reference column, and the 1024 SASS is reported but not committed.

If you remember three things: the launch is the contract, ownership is the architecture, and state read under a predicate must be defined unconditionally.

1. The wrong answer

A broken compiler does not crash. It hands you plausible numbers.

I said that in the recorded video, and it is the sentence that organized the project. The 64 by 64 attention kernel was the proof. It compiled, it assembled, it ran, and it returned numbers with the right shape and the right dtype. Three of the four output rows were the mean of v. The fourth was correct.

The design note records the cause. The kernel has four dot products over a2 inside one loop over a1. Each dot owns an accumulator. The first seeder associated each accumulator with the axis name. When the second loop opened, the seeder reset all four siblings to the same state. Three rows stopped being independent dot products and became the same sum divided by the same denominator.

I had treated the IR as the contract. It is not. The launch, the parameter order and the memory budget live beside it in meta.json. The compiler was not one big translation. It was a stack of small proofs, and every proof had a failure that taught the next invariant. The question that drove the rest of the work was simple: what does the machine actually execute?

2. The contract and the shape of the compiler

The input is a typed statement tree. Tile, Load, Write, Accum, Let, Assign, Cond, Sync, Smem, WarpShuffle, TreeHalve, CpAsyncCopy, ZeroPrologue, and the documented expression nodes. The second input is meta.json: the entry name, arg_order, grid, block, shared-memory budget, and the argument descriptions. The command is one line:

python compile.py kernel.ir.json > out.ptx

Five modules, one emission walk

The module shape is five jobs. ptxc/lower.py owns the prologue, the Tile decode, the cache selection, the top-level seeds and the module assembly. ptxc/stmts.py owns the statement walk, including the loop-entry seeds. ptxc/expr.py owns expressions, indices and predicates. ptxc/memory.py owns addresses, shared layout and alignment. ptxc/common.py, ptxc/ops.py and ptxc/emitter.py own the tables and the text. There is no intermediate IR.

The smallest real example is p00. It has 64 cells, a block of 256 threads, and two elements per cell. The IR says:

Tile[a0] (N=64)
    in0__u0 = load x0[(a0 * 2) + 0]
    in1__u0 = load x1[(a0 * 2) + 0]
    f32 v0__u0 = add(in0__u0, in1__u0)
    in0__u1 = load x0[(a0 * 2) + 1]
    in1__u1 = load x1[(a0 * 2) + 1]
    f32 v0__u1 = add(in0__u1, in1__u1)
    add[(a0 * 2) + 0] = (v0__u0, v0__u1)

The compiler emits a header, a signature, and a guard. The header names the kernel; the signature follows arg_order; the guard compares the flattened work id against the tile size:

.visible .entry k_add_pointwise(
        .param .u64 param_x0,
        .param .u64 param_x1,
        .param .u64 param_add
)
.maxntid 256, 1, 1
...
        mov.u32 %r1, %tid.x;
        mov.u32 %r2, %ctaid.x;
        mov.u32 %r3, %ntid.x;
        mad.lo.u32 %r4, %r2, %r3, %r1;
        setp.ge.u32 %p1, %r4, 64;
        @%p1 bra $L1;

The entry name is the kernel name. The parameters follow arg_order, not the IR node's input order. Buffers are .u64 pointers; scalars are typed .param values. The launch geometry is read from meta.json; the compiler does not infer it. The guard is not decoration. 256 threads are launched for 64 cells, so 192 threads must do nothing. One comparison covers all of them.

That is the contract in plain language. The compiler is allowed to choose instructions. It is not allowed to choose the launch.

The eligibility boundary

Emmy supplies the IR types and the deserializer (Graph.from_dict); the compiler never calls the renderer. The compiler does not call render_kernelop, emmy compile, nvcc, NVRTC, or generated CUDA. Every PTX instruction is emitted by this compiler. The runner assembles the emitted PTX with ptxas downstream. The public repository is one squashed code commit plus three README-only commits that add and correct the video link (68bc29e, 38e7e22, 0420989); the working history is longer. The public artifact is the thing a reader can inspect. The process record is not the artifact.

This boundary is worth stating precisely because the task's rule is about the translation, not the file extension. A submission that chains Emmy's CUDA renderer to nvcc -ptx would produce working PTX and would not be eligible. The compiler here starts at the Kernel IR and ends at PTX text. The only external package in the compile path is Emmy, used for the IR types and the deserializer, never the renderer.

The first working compiler passed all 15 open problems. It was also about 43 times the fast end of the m01 reference range: 6024 microseconds on the local RTX 3050 against 141 microseconds, 30 times the 200 microsecond slow end. The working log records the range but not the reference implementation's identity or GPU. The first working compiler was correct enough to pass. It was not fast on the machine.

3. The three invariants

The first working compiler passed. The promise the early versions broke was the launch.

A compiler is a set of promises about which register is live, which thread is active, and which memory is initialized. The invariants are the promises that survived contact with the GPU. Every optimization in the next section depends on them being true, so they come before the speed work.

Invariant 1: the launch is the contract

The compiler flattens the block and thread ids into one work id:

gid = blockIdx.x * blockDim.x + threadIdx.x
idx_i = (gid / suffix_i) % extent_i
suffix_i = product of the extents to the right of axis i

The suffix divide and the modulo turn one linear id into a coordinate. The final modulo is not optional. The final guard is not optional either. The guard is a single comparison:

if (gid < N) { ... }

That one comparison is correct for every over-provisioned launch because the decode is exact for every gid, including the ids that fall outside the tile. p00 is the smallest case: 64 cells, 256 threads. The first 64 threads own work; the other 192 skip the body. The same pattern covers a 2D row reduction where the launch has more threads than rows.

An exact launch skips the guard. When the launched thread count equals the tile size, every thread owns a tile and the comparison is provably true. The compiler emits the guard only when N < launch (ptxc/lower.py:818). The optimization is safe because the condition is a static property of meta.json and the tile, not a guess. The open set includes both exact and over-provisioned launches.

I got this wrong twice. The design note records both. The final modulo was skipped. In a 2D row reduction, that made every thread start at its global id, and only the leading rows were written. The guard was also missing in an early version, so the over-provisioned threads read past the end of the buffer. The fixes are in _emit_tile and _gid (ptxc/lower.py:736 and ptxc/lower.py:828). The guard is emitted at ptxc/lower.py:818-825. The open-set contract and the over-provisioned pointwise case are the tests. The lesson is that a guard is not defensive decoration. It is the correctness proof for an over-provisioned launch.

Invariant 2: a seed belongs to the loop statement, not the axis name

The loop body is emitted once. An accumulator is a register that the fold writes back into on every iteration. If the seed is wrong, the fold is wrong for every iteration after the first one.

a01 makes the problem concrete. It has four dot products over a2 inside one loop over a1:

for a1 in 0..64
    for a2 in 0..64: q[row0, a2] * kt[a2, a1] -> acc0__ar0
    for a2 in 0..64: q[row1, a2] * kt[a2, a1] -> acc0__ar1
    for a2 in 0..64: q[row2, a2] * kt[a2, a1] -> acc0__ar2
    for a2 in 0..64: q[row3, a2] * kt[a2, a1] -> acc0__ar3
    online softmax update

Each of those four loops owns a separate accumulator. The first seeder keyed the seed by the axis name, a2. When the second loop opened, the seeder reset all four siblings. Three rows collapsed to the same wrong value, the mean of v. The design note records this symptom. There is no saved failing dump from that run, so the design note is the record.

The fix is ownership. _accums_for_loop (ptxc/common.py:87) walks the loop body and stops descending when a nested loop shadows the same axis name. _emit_loop_seeds (ptxc/stmts.py:1395) seeds only the accumulators that the loop instance owns. An accumulator with an explicit Init is seeded by that statement instead. The regression test is the accumulator-ownership unit test, and a01 is the end-to-end case. The lesson is that ownership is the architecture. A register is not merely a name; it belongs to a particular loop instance.

Explicit Init is the other half of the rule. m02 declares its accumulators with a literal identity, so the seed is a statement inside the tile rather than an entry on a loop. The same ownership question applies: the seed belongs to the declaration that owns it. The compiler seeds explicit Init statements separately from loop-entry accumulators, and the tests cover both.

Invariant 3: state read under a predicate is defined unconditionally

The reduction kernels fold state with a warp shuffle and a shared-memory tree. The shared tree needs a base address. The first compiler materialized that base at its first use. In the reduction, that use sits inside if (lane == 0). Every other thread then used an undefined address, and the runner reported an illegal memory access.

The fix is to define the state on the path that every thread takes. _emit_smem_bases (ptxc/memory.py:51) materializes every shared base in the prologue. _emit_thread_helpers (ptxc/lower.py:680) does the same for lane, warp and thread_id. The cache fill and its barrier also run before the over-provisioning guard, for the same reason: every thread in the block has to reach the barrier. The tests are the reduction kernels and the machinery test for nested axis bindings. The design note also records an axis-shadowing case: a sibling loop reusing _fa in the matmul froze a stale counter inside a hoisted expression and produced out-of-bounds cp.async destinations; the address cache is cleared per hoisted copy. The lesson is simple: define it before the branch, not inside either arm.

The three promises together

The launch promise says which threads are active. The ownership promise says which register is live for a given loop instance. The initialization promise says which memory is defined for every thread that can reach it. A bug in any one of them produces plausible numbers or a runtime fault, not a compile error. That is why these three are the architecture and the rest is optimization.

4. The performance descent

With the three promises in place, the compiler was correct on the tested envelope. It was not fast.

The method comes before the numbers. Warm is 10 warmup launches and 100 timed iterations. Cold is 0 warmup and 1 iteration, which is what the scoring harness sees. S1 is the main session; S2 and S3 are labeled rechecks. The runner reports a median, often quantized to 32 ns. Warm differences at or below one tick are noise. Cold differences need non-overlapping ranges or a median gap above 1.5 percent. Absolute numbers move with the runner clock: the same m02 binary measured 3.30 and 5.02 microseconds in two sessions while p00 and 2048 stayed near fixed. The matrix is interleaved, and every cell carries its session label.

4.1 The 43x matmul

m01 took 6024 microseconds in an early measurement on the local RTX 3050 when the reference was 141 to 200 microseconds. The compiler was correct on all 15 open problems. The SASS was not fast. The stage index ((_ks / 64) % 3) had been lowered as a 64-bit remainder. ptxas expands a 64-bit remainder by a small constant into an out-of-line call, CALL.REL.NOINC $__cuda_sm20_rem_s64, and that call sat in the innermost loop four times per iteration.

The fix was 32-bit index arithmetic. idx32 (ptxc/expr.py:501) compiles an index expression into one 32-bit register, matching the C int coordinates in Emmy's renderer. The runner caps buffers at 2^26 elements, so 32-bit arithmetic is exact. rem.s32 inlines to a multiply-high sequence. The working log records the local result as 6024 to 206 microseconds on the RTX 3050, about 29 times faster, and the hosted result as 584 to 41.6 microseconds on the RTX 5090, about 14 times faster. The final m01 warm median is 13.872 microseconds after the rest of the stack.

before: rem.s64  -> CALL.REL.NOINC $__cuda_sm20_rem_s64
after:  rem.s32  -> multiply-high sequence, inline

The before and after shape is the whole lesson. The 64-bit remainder became an out-of-line call in the hot loop; the 32-bit remainder inlined.

The lesson is to read the machine code. A high-level theory about the schedule would not have found this. The disassembly did.

4.2 Launch bounds

The attention kernels are latency-bound with one block per SM. Without .maxntid, ptxas budgets registers for a 1024-thread block. a02 was capped at 56 registers. Emitting the real block size raised the budget to 80 registers at that point and cut the warm time from 43.7 to 25.2 microseconds. The working log records the a02 budget as 56 before and 80 after; the 80 is a02's ptxas budget, while the 255 in the four-dot row is a different kernel's budget. The line is one string in _signature (ptxc/lower.py:627):

.maxntid 32, 1, 1

That is the a02 block size; a01's is 128. The point is the same: the launch descriptor already knows the block size, so the compiler should tell ptxas instead of letting it assume the worst case. The lesson is that an assumption can be the bottleneck. No instruction was removed. The register budget changed.

4.3 The tile cache

A block of attention re-reads the whole key tile from global memory for every key. The tile is 16 KiB, so it fits in shared memory. One cooperative fill, transposed when the dot axis is the leading coordinate, replaces thousands of global loads with 128-bit shared loads.

The transposed fill is the part that is easy to get wrong. The fill reads four consecutive keys from one source row. Those four keys land on four shared rows, so the store stride is the row extent of a2, not 1. The first version wrote +j and broke the answer. The open set caught it.

The results in the experiment session were a01 warm 49.8 to 25.2 microseconds, and a02 from its own 25.2 pre-cache baseline to 13.0 microseconds. The final S1 medians are 27.136 and 10.816; the sessions differ and the rest of the stack landed later. The cache commit recorded 27.3 microseconds for a01; the experiment log recorded 25.2 in its session; the final S1 median is 27.136. I report all three.

// a01 decode: one gid becomes four axes
div.u32 %r7, %r6, 256;
rem.u32 %r8, %r7, 2;
div.u32 %r9, %r6, 128;
rem.u32 %r10, %r9, 2;
div.u32 %r11, %r6, 16;
rem.u32 %r12, %r11, 8;
rem.u32 %r13, %r6, 16;

// transposed kt fill: four keys, four shared rows
shr.u32 %r23, %r22, 6;      // column
and.b32 %r24, %r22, 63;     // row
mad.lo.s32 %r25, %r24, 64, %r23;
st.shared.f32 [%r26], %f5;
add.s32 %r29, %r25, %r28;   // +64
add.s32 %r33, %r25, %r32;   // +128
add.s32 %r37, %r25, %r36;   // +192

The decode turns one gid into four axes. The transposed fill stores four consecutive keys into four shared rows with stride 64. The wrong +j stride would put all four keys in consecutive slots.

The lesson is to derive the stride from the layout. Pattern-matching the source index gives +j; the shared layout gives +j * a2.

4.4 The slice cache

A large q does not fit whole. A block reads only its own rows, and those rows are contiguous because blocks partition the leading dimension. The fill starts at the block base, and the loads subtract the same base. The 256 by 128 attention shape went from 1434 to 947 microseconds warm. The selection ranks candidates by estimated instruction saving, so a small key tile wins when only one cache fits. The lesson is that the right cache is the one that fits the block's working set, not the one that fits the whole tensor.

4.5 The warp dot

In a one-row-per-warp schedule every lane computes the same score. The compiler splits the head axis across lanes: each lane sums head / group terms, then a butterfly shuffle adds the partials into every lane. The group is 16 for a01, because two rows share a warp, and 32 for a02, because the whole warp shares the dot.

shfl.sync.bfly.b32 %f45, %f36, 8, 0x1f, 0xffffffff;
add.f32 %f36, %f36, %f45;
shfl.sync.bfly.b32 %f46, %f36, 4, 0x1f, 0xffffffff;
add.f32 %f36, %f36, %f46;
shfl.sync.bfly.b32 %f47, %f36, 2, 0x1f, 0xffffffff;
add.f32 %f36, %f36, %f47;
shfl.sync.bfly.b32 %f48, %f36, 1, 0x1f, 0xffffffff;
add.f32 %f36, %f36, %f48;

For a01's 16-lane group, the four shuffles and adds are the whole reduction; a02's 32-lane group uses five. The full mask keeps the shuffle inside the active warp.

The results were a02 warm 13.0 to 10.9 microseconds and the 256 by 128 shape warm 947 to 257 microseconds. a01 did not improve when its dot became cooperative: 25.25 warm before and after. That is a useful negative result. The online-softmax dependency chain and the shuffle tree are its bound. Adding more machinery there would not address the bound. The lesson is that a negative result is data.

4.6 The m01 pipeline

m01 is a three-stage cp.async pipeline. Each stage copies one a slab and two b slabs into shared memory, commits the group, and then waits until at most two groups are in flight. The inner loop is 64 steps, fully unrolled, with literal shared offsets.

cp.async.cg.shared.global [%r138], [%rd20], 16;
cp.async.cg.shared.global [%r148], [%rd22], 16;
cp.async.cg.shared.global [%r158], [%rd24], 16;
cp.async.commit_group;
cp.async.wait_group 2;
bar.sync 0;
ld.shared.v2.f32 {%f5, %f6}, [%r164];
ld.shared.f32 %f7, [%r167];
fma.rn.f32 %f1, %f5, %f7, %f1;
fma.rn.f32 %f2, %f6, %f7, %f2;
fma.rn.f32 %f3, %f5, %f8, %f3;
fma.rn.f32 %f4, %f6, %f8, %f4;

Three cp.async copies fill the next stage; wait_group 2 leaves two groups in flight; the inner loop reads the shared tile with vector and scalar shared loads and four FMAs per step. This listing is an excerpt. At the LDS.64 fusion, the 1024 vector loads were across the 64-step unrolled loop, 16 per step; the final m01 after the cp.async pipeline has 512 ld.shared.v2.f32 and 1024 ld.shared.f32. The table's 1024-vector count is the fusion's measured effect, not the final static count.

The four-dot fusion

The four-dot fusion looked right. a01 has four dot loops over the same a2 axis and the same kt column. Fusing them would remove duplicate key-column loads: 540 lines and 42 loads instead of 680 and 66. The instruction count went down.

The machine did not care. ptxas dropped the register budget from 255 to 96 registers, and the kernel doubled to about 95 microseconds in that session. The redundant loads were cheaper than the scheduling freedom they bought. The fused version had fewer instructions and less room to hide latency. That is the scheduling-freedom lesson in its purest form: a shorter kernel can be slower.

The 1024 holdout

The 1024 by 1024 by 1024 holdout is the one disclosed residual. It runs at 70.208 microseconds warm and 81.568 cold. The hosted SASS is 1268 instructions on the RTX 5090 (sm_120, CUDA 12.9); the local SASS is 1240 from ptxas 12.6 targeting sm_89, and the local GPU is an RTX 3050 (sm_86). The holdout meta launches 88 blocks of 512 threads on a 170-SM GPU, so it runs less than one block per SM. The next work is the ptxas schedule, not a missing mechanism.

The evidence here is an instruction count and a launch shape, not a committed SASS file. The private audit recomputed 45 wins, 42 ties and 1 loss from a CSV that carried the reference medians. The public CSV carries the absolute medians, not the reference column, so the 45/42/1 verdict is private-audit evidence. The absolute numbers are the public evidence.

7. The boundary and the lessons

The artifact passed the gates. The gates are not the boundary.

A private final audit found seven edge failures that the open set, the variants and the corpus do not exercise. They are the boundary of the proof, not a confession.

failure what happens why the proof does not cover it
f16/f64 bare truthiness Cond or where on an f16 or f64 value emits setp.neu.f32 on a %h or %d register; ptxas rejects the operand mismatch the public tests cover f32 truthiness only
grouped shared v4 from a 4-byte-aligned pool offset a four-name shared load can be 16-byte misaligned because _load_consecutive does not check the declaration alignment _plan_pairs checks alignment, but the grouped path does not
divergent Cond containing bar.sync only the threads inside the predicate reach the barrier, so the block can hang the partial-block guard catches a barrier under an over-provisioned launch, not a divergent barrier on an exact launch
16-byte cp.async with a 4-byte source offset the compiler emits a 16-byte copy to a 4-byte-offset source; a local run reports a misaligned address at runtime the reference IR uses 16-byte-aligned indices
TreeHalve length above the block's warp count slots above the active warps are uninitialized; the sum is wrong the task schedules satisfy the length, and there is no length-versus-block check
WarpShuffle length not a power of two the emitter folds offset length/2 ... 1 and ignores the missing lane; the result is wrong no power-of-two check
scalar bool parameter the signature emits .param .pred; ptxas rejects the parameter and the ld.param.pred numeric scalars are tested; bool is not

Table 6. Seven constructs outside the tested envelope. The public README's "fails loudly" covers unknown constructs and malformed input; it does not list these seven silent failures in implemented constructs. A CompileError on a hidden problem still scores zero for that problem.

Separately, the public coverage page lists the unimplemented constructs: the tensor-core and TMA star constructs, Select, Pre, Carry, FuncCallExpr, shared read swizzle, and f64 max.NaN/min.NaN. Those raise CompileError; the seven above are the silent failures in the implemented set.

These failures are the next work, not a reason to distrust the 15 open problems. The open problems are a sample, and the sample is green. The boundary is what the sample does not cover.

The lessons are tied to the stories:

  1. Read the machine code. The 43x bug was invisible in the Python and obvious in SASS.
  2. The launch is the contract. A guard is not defensive decoration; it is the correctness proof for over-provisioned launches.
  3. Ownership is the architecture. Seeds belong to loop instances, shared bases belong to the prologue, and caches belong to a basic block.
  4. Scheduling freedom is a primary constraint. A shorter kernel can be slower. Redundant loads can buy scheduling freedom.
  5. Measure, interleave, reject. A single cold sample is not evidence. A negative result is data.
  6. The last percent is often the scheduler. When the instruction mix matches and the gap remains, do not add a mechanism.
  7. A public claim needs public evidence. Absolute medians, sample counts, session labels and a disclosed residual are stronger than a ratio with no column.
  8. Strict inputs are a feature. A compiler that invents a launch is not being helpful; it is hiding a broken package.

What I would do next

This is an independent write-up, not part of the hackathon submission. The hackathon submission window is closed. The next steps are for the compiler as a standalone project.

The next steps are concrete. Fix the dtype truthiness paths so an f16 or f64 condition emits a comparison on the right register class. Check the shared declaration alignment on the grouped v4 path. Validate TreeHalve and WarpShuffle lengths against the block and the power-of-two requirement. Add an alignment proof or a scalar fallback for cp.async. Publish the reference column and the raw per-round JSON so the comparison verdict is reproducible from the public tree. Run the exact public commit on a clean GPU and archive the log. Test the edge cases the private final audit found before the broad cases: scalar parameters, over-provisioned collectives, partial warps, f16/f64, and multi-kernel chains.

The compiler is in the repo, the tests are in the repo, the benchmark matrix is in the repo, and the one residual cell is in the matrix too. The interesting part is the distance between the original wrong answer and the last measured one.
